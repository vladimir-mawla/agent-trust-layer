1 · The Locked Spec (what we are building)

Cognitive job: Decide whether one agent should act on another agent's request, by verifying cryptographically signed claims about who that agent is, what authority it was granted, and what it has done before.

Inputs: A counterparty agent's DID, a signed presentation of its verifiable credentials answering a freshness challenge, and the specific action being requested with its parameters.  →  Outputs: An accept or refuse decision, plus a machine-readable explanation naming the exact rule that fired and the exact credential field that satisfied or failed it.

Autonomy level: Fully autonomous for decisions the policy covers; the policy itself is authored by a human and every decision is explainable after the fact.  |  Human-in-the-loop points: Humans author policies, choose which issuers to trust, and grant or revoke the authority credentials that agents present. No human is in the per-decision loop.

Failure tolerance: Fail closed. An unverifiable, expired, revoked, or unparseable credential is treated exactly as an absent one, and the request is refused rather than allowed through.  |  Trust boundary: Everything a counterparty presents is untrusted until its signature verifies against the issuer's key. Possessing a DID string proves nothing; only signing a fresh challenge proves key possession.

Filled during Genesis step G0 (Cognitive Design) via agentic-swe-master.

2 · Definition of Done (binary gates — checked by the VERIFIER, not the maker)

Dependency direction inward, zero cycles (modular-architecture gate)
npm run typecheck clean AND npm test green in CI
One verify pass by a separate agent/model (L4)
No context-graph.json invariant violated by the change
Every credential's signature is verified before any claim inside it is read (trust-boundary gate)
A presentation that replays another agent's credential is rejected on subject binding (anti-replay gate)
A spoofed agent presenting a copied DID is rejected at proof-of-possession, before any credential is even examined (anti-impersonation gate)
Every trust decision returns a structured explanation naming the rule and the credential field (explainability gate — no bare booleans)
No private key material appears in any response, log, or committed file, provable by grep over the full history (key-hygiene gate)
The live demo URL returns 200 to an anonymous request (deliverable gate — the brief requires a live demo)
A clean clone plus install plus test passes with no credentials configured (clean-clone gate)

A milestone is DONE only when every box above is checked by the verifier. There is deliberately no LLM in the trust path, so the llmops schema-validation gate and the timeout/circuit-breaker gate from the generic template do not apply here and were dropped.
